# Linux acceptance procedure

Unit/fault tests are available now. This checklist has **not** been completed against a real Linux VPS. Do not use the first implementation for production changes until acceptance evidence has been recorded.

Use a disposable VPS with no production applications or credentials, a dedicated test domain/Cloudflare zone, a test control CA/client certificate, and the exact Docker/Compose/Caddy versions you intend to deploy. Build two approved GHCR image digests that serve a version identifier, a readiness endpoint, a failing-readiness mode, a 30-second request endpoint, and a stream/WebSocket endpoint. Include the health command specified by the root template.

1. Run the Linux builder's race tests/vet and record architecture, distribution, libc, Go/toolchain, Docker/Compose, Caddy, and image digests. Test systemd startup, graceful stop, process locking, and child process-group cancellation on Linux.
2. Verify missing/untrusted/wrong-pinned client certificates and invalid/expired/body/query-tampered HMAC requests cannot read privileged APIs or create side effects. Verify key scope and per-project boundaries, credential revocation, queue quotas, and unauthenticated rate limiting.
3. Create a project with explicit ports and another with automatic ports. Confirm private root-owned Compose/environment files, loopback-only port publishing, the enforced runtime security/resources, and maintenance until first activation. Refuse existing `/docker` directories, manual Caddy hostnames, reserved hostnames/ports, wildcard listeners, Docker port reservations, and concurrent reservation races.
4. Deploy A to blue, B to green, then A to blue. Inspect actual image IDs, literal environment values, readiness, labels, host bindings, live Caddy routes, and drain behavior. Run continuous normal HTTP traffic through Caddy for at least 100 alternating deployments and record every response/error and transition.
5. Hold 30-second requests open during switches and confirm they finish inside the configured drain interval. Record stream/WebSocket behavior explicitly; finite drain does not promise indefinite connection preservation.
6. Inject failed pulls, startup failure, readiness failure, wrong image/environment identity, validation rejection, rejected reloads, reload timeouts before/after application, Caddy admin unavailability, database commit failures, disk-full conditions, and failed old-slot cleanup. Confirm old serving state survives pre-switch failures; unknown outcomes preserve both slots and block new work.
7. Kill the agent immediately before/after candidate binding, container startup, route file write, reload, metadata activation, and drain/cleanup. Reboot the VPS during relevant phases. Run offline reconciliation, confirm actual observed state, and verify a fresh drain before slot reuse.
8. Confirm rollback/restored start uses the exact previously activated image/environment pair. Check single-slot downtime and failure-in-maintenance behavior. Confirm `stop` requires the exact project ID, routes to maintenance before stopping, and never removes volumes or unrelated containers.
9. Update domains while running; change ports only while stopped. Test collisions and unrelated Caddy sites. Confirm each key sees/logs only its assigned projects. Verify bounds/redaction for known retained secrets and truncated logs; document transformed application-secret limitations.
10. Create a permitted Cloudflare subdomain pointing at the configured origin IP. Test retry after a simulated timeout, rejection of foreign/CNAME/NS records, zone/suffix boundaries, provider rejection, and domain/Caddy association. Check DNS propagation and public TLS separately from configuration success.
11. Exercise backup/restore of matching state, file revisions, Caddy config, and the fingerprint key. Test root-policy/key replacement, credential incidents, history-quota exhaustion, and failed initial provisioning recovery procedures.
12. Upgrade an existing database and verify projects, jobs, retry identities, slot/domain reservations and audit history survive. Compare the new service/domain inventory with recorded state, including retired domains and DNS IDs after a successful DNS job. Temporarily make a project directory unavailable while the agent runs: inventory must remain readable, while lifecycle/status checks must refuse missing artifacts. Restore files and verify startup integrity checks. Inject a metadata-index write failure and confirm project/job/audit updates roll back together.

Keep a dated evidence report with command/tool versions, safe test outputs, traffic counts, fault outcomes, and unresolved items. Never publish secrets, client private keys, raw Docker inspect output, or application environment dumps in that report.

## Environment acceptance

Test one-shot/startup/periodic discovery against existing Compose directories, Caddy imports, static and nested proxy sites, stopped/running containers and out-of-directory Docker workloads. Compare inventory with the real topology; check warnings for unresolved interpolation/aliases/overrides and unassociated upstreams. Prove files and services remain unchanged, secrets never reach SQLite/API/logs, failed sources retain prior data, and observed ports cannot be allocated. Test daemon crash/restart, Docker/Caddy restart, host reboot and explicit operator stop under the revised systemd unit. Exercise a representative 50–100-service host; unit discovery of 100 directories does not replace live load testing.

Create the same app in development, staging and production with separate IDs/domains. Verify independent ports, networks, volumes, private environment files, jobs and release history. Reject a second deployment with the same app/environment, non-production blue-green/secondary ports and wrong or omitted deploy environment before changes. Check per-project key policy prevents a development-only key from accessing production, even with the same app ID. Upgrade a version-1 database containing both single-slot and blue-green projects plus queued/recovery jobs; confirm they retain their IDs/paths/modes as production and retries survive. Exercise the CLI prompt and unattended flag with stable retry IDs. Development/staging updates must replace only their single slot through maintenance; repeat production traffic/failure tests across both slots.

## Submitted Compose acceptance

Submit app + companion stacks and confirm every image/template/environment is authorized, validation completes before 202, and no submitted source reaches Compose’s loader. Try host binds/sockets, privileged containers, devices, host namespaces/networks, include/extends, build contexts, file-backed secrets/configs, external volumes/networks, volume driver options, duplicate keys, anchors/aliases, custom tags, oversized YAML, missing/cyclic dependencies, forged labels, and public ports. Confirm all fail before resource changes. Test failures from the normalized Compose config check as well.

Deploy two stateless stack revisions with different app/companion images and service sets. Prove the serving slot retains its exact manifest and every companion must be healthy before Caddy switches. Verify per-service logs redact secrets from all retained service environments. Test restart/rollback/stop and foreign companion ownership; no stack stop may run before all services are identified.

For a single-slot app/database project, write a test record, deploy/restart/stop/start/rollback and verify the same volume identity and data survive. Check foreign existing volumes, local driver bind options, unexpected/anonymous mounts and modified immutable manifests are refused. Confirm persistent Compose YAML is rejected in blue-green mode. Test UID/permissions and application-consistent volume backup/restore; container rollback must never claim to roll back database schema/data. Partial failed stack starts need an explicit tested local recovery procedure before reusing the slot. Cleanup of removed services/volumes remains manual.
